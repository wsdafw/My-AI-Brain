# PAIOS · 设计原则

文档版本：1.0.0 | 架构目标：V1.1 | 状态：Accepted

更新时间：2026-11-11（Asia/Shanghai）

## 核心原则

1. **系统独立于工具**：先定义职责、输入、输出和验收，再选择模型或软件。
2. **本地、开放、可移植**：系统文档和知识正文使用 Markdown；链接、来源和上下文应能脱离特定聊天平台理解。
3. **规范只有一个主来源**：正式规范保存在 `00_System/`；平台指令是带版本标识的副本，更新从主来源向外分发。
4. **经验必须回流**：L5 的复盘通过实验、评估和决策反馈到 L0，不只保留在聊天中。
5. **先验证，再标准化**：区分事实、假设、建议、试验结果。未验证的方案标为 Proposed，不宣称有效。
6. **保留设计理由**：重要架构选择记录 ADR，包括替代方案、代价、证据和重审条件。
7. **最小可行复杂度**：手工流程能解决的问题先手工验证；引入插件、自动化或多 Agent 必须有具体瓶颈与收益依据。
8. **保护已有资产**：检查实际文件后再写入。没有授权不删除、重命名或覆盖笔记；同名内容存在时先比较，再提出合并或另存方案。
9. **可追溯与可恢复**：变更关联任务、决策和验证记录；Git 保存历史。正式发布前能说明如何恢复。
10. **人负责最终取舍**：AI 协助，不伪造用户意图、接受状态、来源、运行结果或历史。

## 实施约束

- 系统文档须有标题、文档版本、状态、更新时间；日期使用 Asia/Shanghai。
- 默认使用普通 Markdown 相对链接；图表须有文字说明，避免关键信息只能由插件解释。
- 不在规范、日志和提交中保存 API 密钥或账号凭证；调用模型前确认输入符合任务授权范围。
- 不能把“有文件”“有提交”或“有输出”当成效果证据。
- 检查工具真实能力；不承诺自动同步、永久记忆、跨模型兼容或 Harness 能力已经实现。

## 冲突处理

当前用户明确授权及执行环境的安全约束必须得到遵守。PAIOS 文档内部的矛盾应记入复盘；涉及原则、层级职责、主来源或工具依赖的修改须通过 ADR 和 [Evolution](Workflows/Evolution.md) 处理，不静默改写历史理由。
