# PAIOS · 版本与 Git 策略

文档版本：1.0.0 | 架构目标：V1.1 | 状态：Accepted（策略）

更新时间：2026-11-11（Asia/Shanghai）

## 三个概念分开

- **架构称呼**：`V1.1`，指本次六层架构方向。
- **系统版本**：`Major.Minor.Patch`；目标 `1.1.0` 当前为 Proposed / 未发布。
- **文档版本**：各文档自身版本，初次成文为 `1.0.0`，与系统发布时间不同步。

| 类型 | 变更范围 | 示例 |
| --- | --- | --- |
| Major | 核心架构或职责发生不兼容变化，影响现有工作方式 | `1.x.x → 2.0.0`，经验证后改变核心执行架构 |
| Minor | 在现有框架中增加兼容能力 | `1.1.x → 1.2.0`，新增已验证的研究辅助能力 |
| Patch | 修正模板、规则、链接或局部流程，不改变核心职责 | `1.1.0 → 1.1.1` |

V1.1 是用户指定的目标标识，不表示已经存在 V1.0 发布。后续升级按真实变化判断；不能为了匹配预设版本号弱化重大变更。

## 状态与证据

| 状态 | 含义 |
| --- | --- |
| Proposed | 候选、试行或待评估；不能作为已验证的正式流程 |
| Accepted | 负责人明确选定的原则或决策；流程被接受还需附验证证据 |
| Rejected | 已评估但不采用；保留原因 |
| Superseded | 已被后续记录替代；双向关联新旧 ADR，保留历史理由 |

实验结果另外使用“未开始 / 进行中 / 通过 / 未通过 / 证据不足”，不与 ADR 状态混用。文档中任何局部 Proposed 标记优先限定该条内容的适用范围。

## Git 管理边界

实际仓库根目录为 `My AI Brain/`；父目录 `E:\Personal-AI-OS` 本次检查不是 Git 仓库。检查开始时仓库无提交、无远端，业务笔记和 Obsidian 配置均未被跟踪。

本次治理基线仅将 `00_System/` 的文档纳入本地提交；现有业务笔记、`.obsidian/` 和 Vault 外代码的跟踪范围待单独确定。Git 本地历史不等于异机备份；远端、备份位置及同步策略保持待定，不自动建立服务或上传内容。

提交习惯：一个提交围绕一个可说明的变更，列明相关 ADR/实验；在仓库根目录执行 `git status --short`、核对具体文件后显式暂存，再用 `git diff --cached` 审阅。避免使用全量添加把无关笔记或本地配置混入治理变更。

## 正式发布流程

1. 明确发布范围、关联 ADR 和原先冻结的验收条件。
2. 完成真实任务验证；V1.1 首发至少包括研究实验、学习和开发流程各一次试用、一次可移植性检查及一轮完整演进记录。此首发验收范围为 Proposed，开始实验前由负责人确认或调整，不能事后迁就结果。
3. 证据充分后，由负责人接受经过验证的流程；未验证内容明确排除在正式范围外。
4. 更新架构、相关流程/AI 指令、版本状态、CHANGELOG、ROADMAP，并链接实验及 ADR。通过链接检查、范围检查和差异审阅。
5. 提交发布文档，再在该提交上建立 `vX.Y.Z` 标签；不得提前给 Proposed 文档打正式标签。
6. 将平台指令副本更新到该版本，记录分发日期。只有文档完成但没有实际验证时，仍留在 Unreleased。

## 迭代节奏与恢复

- 每周检查体验、记录问题、尝试小改进；每月评估架构、复审 ADR、决定是否升级。不是每周或每月都必须发布。
- 文案改进可有普通 Git 提交，无需为每次修改发布系统版本。
- 出现回退需求时，先保存当前未提交工作并核对受影响文件，再用新提交恢复已知有效状态（例如针对明确提交使用 `git revert`）。不执行未经确认的整体重置或批量删除。
- 试行失败时记录失败与恢复路径；若改变已接受的重要决策，新增 ADR 或记为 Superseded，不能擦除原理由。
