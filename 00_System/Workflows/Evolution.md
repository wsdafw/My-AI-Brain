# PAIOS · Evolution Cycle

文档版本：1.0.0 | 架构目标：V1.1 | 状态：Proposed（操作流程）

更新时间：2026-11-11（Asia/Shanghai） | 六步闭环方向：Accepted，见 ADR-004

## 从运行经验回到系统规范

| 阶段 | 要回答的问题与操作 | 最小产物 | 进入下一步的条件 |
| --- | --- | --- | --- |
| 01 · Observe | 问题何时、何处发生，影响什么？ | 复盘中的实例、频次、任务/成果链接 | 有观察证据；假想问题明确标记 |
| 02 · Diagnose | 是格式、操作成本、知识缺口还是工具故障？ | 根因假设、替代解释、当前基线 | 不把相关性当根因，知道要验证什么 |
| 03 · Design | 哪个最小改动能检验假设？ | Proposed 实验；重要架构变化另建 ADR | 明确范围、成功标准、成本、失败及恢复办法 |
| 04 · Implement | 在哪里试行，具体改了什么？ | 试行产物、版本/文件清单、过程记录 | 在授权范围内可复现，正式流程不被静默替换 |
| 05 · Evaluate | 是否改善任务？是否造成回退？ | 原始数据、比较、局限、通过/未通过/证据不足 | 结论对应预先标准；不足则返回 Diagnose/Design |
| 06 · Standardize | 哪些内容值得成为规范？ | 负责人判断、更新的规范/ADR/日志和 Git 记录 | 有证据、有适用范围、有恢复路径；再进入下一轮 |

重要架构变化包括：知识主存储、规范权威、层级职责、模型/执行器耦合方式、新的强依赖、外部同步及发布策略。普通文字修正不必创建 ADR。

## Standardize 的完成清单

- [ ] 评估记录可以定位到真实任务和结果，失败项及代价没有被隐藏。
- [ ] 负责人明确接受本次适用范围；无效果或证据不足的提案继续 Proposed 或记为 Rejected。
- [ ] 涉及架构的 ADR 已接受；替代旧决策时保留旧记录并标记 Superseded。
- [ ] 更新受影响的架构、工作流程、评估口径及 AI 指令；注明文档版本和更新时间。
- [ ] CHANGELOG 记录变化与证据，ROADMAP 反映实际进展。
- [ ] Git 保存经审阅的变更；是否发布与标签按 VERSIONING 判断。
- [ ] 更新需要分发的工具指令副本，并记录它们使用的规范版本；未分发则明确列出。

该清单未满足时不能宣称闭环完成。标准化可以只接受局部改进，不强制每轮发布整个系统。

## 最小 ADR 格式

新建前检查编号与文件是否存在，不覆盖原记录。原有 `ADR-001.md`、`ADR-002.md` 保留文件名。

```markdown
# ADR-NNN: 决策标题
文档版本：1.0.0
更新时间：YYYY-MM-DD（Asia/Shanghai）
## Status
Proposed；决策人/日期：待定；验证状态：待验证
## Context
问题、约束、观察证据及关联实验
## Decision
采用或拟采用什么，适用范围是什么
## Alternatives
真实可选方案及取舍
## Reasons
依据；假设明确标记
## Consequences
Positive：预期收益与已证实收益分开
Negative：代价、限制与恢复办法
## Review Trigger
何时、出现什么变化需要重审
## Evidence and Links
实验、复盘、相关规范及替代关系
```

## 示例：研究成果没有进入知识库

这是假设性示例，不是本次已观察到的故障：Observe 记录未保存任务；Diagnose 比较格式不统一与保存步骤繁琐两种解释；Design 先试统一成果协议；Implement 输出兼容既有模板的 Markdown；Evaluate 用三个不同主题并与可比基线比较；Standardize 只有在有效且获接受后更新 Research Workflow。

可执行的首个候选方案见 [EXP-001](../Experiments/EXP-001-Research-Capture.md)，目前没有样本和结论。
